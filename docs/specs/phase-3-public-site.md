## Decisions taken in this spec (recommended defaults, owner pre-approved "recommended solutions")

1. **Images**: `ResponsiveImage` (`src/components/media/responsive-image.tsx`) renders an `<img>` with the attributes `next/image` would give it (`fillImageAttributes()` in `src/lib/images.ts`, since PR I, so no `next/image` client code ships; ADR-029) with a loader for Supabase Storage image transformations (`/storage/v1/render/image/public/media/<path>?width=<w>&quality=75&resize=contain`). No `format` parameter is sent: Supabase then serves WebP (or AVIF where enabled) to browsers that accept it and the original format otherwise; `format=origin`, which turns that conversion off, is never used. The loader is used when `NEXT_PUBLIC_SUPABASE_IMAGE_TRANSFORMS=true` (staging and production, Supabase Pro); otherwise images are served from the plain public object URL with `unoptimized` (local Supabase, CI). Every image passes `width`/`height` from `media`, a `sizes` string per usage, `placeholder="blur"` with `media.blur_data_url`, and the alt text of the current language (`media.alt[locale]`, never empty on published content per ADR-024). The LCP image (hero, gallery lead) gets `priority`. A media row whose file is missing, or no media at all, renders `ImageFrame`, a neutral frame at the same aspect ratio, so layout never shifts. CSP `img-src` gains the Supabase host.
2. **Data access**: public pages read through new read-only modules (`src/modules/catalog/public/*`, `src/modules/content/public/*`) with the session-less public client (`lib/supabase/public.ts`, anon, RLS applies), never the service role and never the admin repositories. Queries select explicit columns. Missing rows return `null`; database errors throw (see decision 12).
3. **Caching (ADR-015)**, using the tags the Phase 2 services already refresh:
   | Page | Cached (`"use cache"`, `cacheLife("hours")`) | Tags | Live (inside `<Suspense>`, after `await connection()`) |
   | --- | --- | --- | --- |
   | Home | sections, featured tours with "from" price and next date | `settings`, `tours`, `destinations`, `travel-styles`, `reviews`, `posts` | — |
   | Tour detail | content, gallery, itinerary, policy, related tours | `tours`, `tour:<id>`, `destinations`, `travel-styles`, `cancellation-policies`, `settings` | departures, seats, prices in the booking box, the tour's JSON-LD offers |
   | Listing, search | filter options (`tours`, `destinations`, `travel-styles`) | | results (`tour-listing.md` §4.2) |
   | Destinations, styles | page and its tours (no seat badges) | `destinations`, `travel-styles`, `tours` | — |
   | Journal, pages, reviews | content | `posts`, `pages`, `reviews`, `settings` | — |
   Cached views never show seat counts or "Sắp hết chỗ" (they would go stale between bookings); only the listing results and the tour detail's live section do. `tour-listing.md` §4.2 names a `catalog` tag: read it as `tours` + `destinations`. Saving a cancellation policy must also refresh `tours` (known issue; PR H adds it to the policy service with the coordinator's agreement, since the policy pages are Stream A's done work). **Phase 4 note**: the booking functions change seats and bookability without an admin save, so cached cards must keep not depending on seats (only price and the next date, which can go stale for up to an hour), or the Phase 4 services must call `revalidateTag("tours")` after a hold, confirmation, expiry or cancellation that changes a departure's bookability. Phase 4 picks one and records it.
4. **Dynamic routes and builds**: `[slug]` routes export `generateStaticParams` with the published slugs of each locale (read as anon). When the read fails or returns nothing, it returns one sentinel slug that renders `notFound()`, so a build during a database outage still succeeds and pages render on demand. Verified against Next.js 16 behaviour in PR H.
5. **Languages**: a page exists in a language only when its row and that translation are published (ADR-006); otherwise `notFound()`, both for missing and unpublished translations. `alternates.languages` (hreflang) lists only languages with a published translation, plus `x-default` → Vietnamese when Vietnamese is published. Canonical is the page's own localized URL.
6. **LanguageSwitcher slug lookup**: each content page renders `<LocaleAlternates links={{ vi, en }} />`, a tiny client component that publishes the page's per-language paths (from the same data as hreflang) into a store read by the existing `LanguageSwitcher` (`useSyncExternalStore`). Without alternates the switcher keeps today's same-path behaviour. When the other language has no published translation, the switcher links to that language's parent page (tour → `/en/tours`, destination → `/en/destinations`, article → `/en/journal`) with `hreflang` and a title saying the page is not available in that language.
7. **Rich text**: destination `content`, posts and pages render through the whitelist renderer `src/components/typography/rich-text.tsx` that Stream A ships in Phase 2 PR F (decision 7 of the Phase 2 spec). Until PR F merges, Phase 3 pages show the plain fields (summary, description, best time to visit) and never raw JSON; PR K starts after PR F.
8. **Display price and availability**: tour cards everywhere use `search_tours()` from `tour-listing.md` §4.3 (display price, next bookable departure, other departure count, seats left). The migration moves from PR L into PR H, because the tour detail's related tours and the homepage need the same numbers. Bookable departure: `open` or `guaranteed`, starting on or after today in Vietnam plus the booking cutoff, with seats left. The cutoff comes from `public.booking_cutoff_days()` (security definer, stable, `search_path = ''`, granted to anon and authenticated), which returns `settings.booking_rules.booking_cutoff_days` or 7: `booking_rules` is not a public setting, and this exposes one number, not the row. The key is a cross-stream agreement (see "Cross-stream agreements"): Stream A adds it to the `booking_rules` shape and the settings editor in PR G; Stream B only reads it. Seats are shown as "Còn N chỗ" (exact count, never capacity); the warning badge "Sắp hết chỗ" appears at 4 or fewer.
9. **Calls to action before Phases 4–5**: `src/lib/features.ts` holds `booking` and `inquiry` flags (both `false` now; Phase 4 and Phase 5 switch them on). While `booking` is off the booking box keeps the departure select and the estimate, and its filled button reads "Liên hệ đặt chỗ" / "Contact us to book" and goes to the contact page with the tour code and date in the query; the hotline sits under it. While `inquiry` is off, tailor-made CTAs go to the contact page too; until the contact page exists (`contactPage` flag, PR K) they offer the hotline and email from settings, like the booking box. The journal teaser waits for the journal routes (`journal` flag, PR K). The newsletter sign-up ships in PR I (coordinator instruction; ADR-029) and is shown disabled until Turnstile, Upstash and Resend are configured. No link ever points at a route that returns 404.
10. **JSON-LD** through one `JsonLd` server component that serialises with `<`, `>` and `&` escaped (`<` …), so content can never close the script tag:
    - every page: `BreadcrumbList` (with the visible breadcrumbs);
    - home and about: `TravelAgency` (also `Organization`) from `settings.company`/`contact`, only fields that are set;
    - tour detail: one node typed `["Product", "TouristTrip"]` with name, description, image, `touristType` from styles, `itinerary` as an `ItemList` of days, and an `AggregateOffer` (VND low/high price over bookable departures, offer count, availability) rendered inside the live boundary; private tours use `from_price` with `priceSpecification` "from". No `AggregateRating` until verified reviews (P1);
    - listing, destination, style pages: `ItemList` of tour URLs; journal articles: `Article`; `/faq`: `FAQPage`.
11. **Open Graph images**: pages with a photo use it directly (the translation's `og_media_id`, else the hero), transformed to 1200×630 by the image loader when transforms are on. Pages without one (home, listing, search, policies) use a generated image from `src/app/(public)/[locale]/(site)/opengraph-image.tsx` (in the page segment: a parent-level file image is replaced when a page sets `openGraph` in its metadata; generated image paths skip the proxy, which would redirect their `/vi/` path) (`next/og`): brand name from settings in Cormorant Garamond on navy with a gold rule, statically generated per locale. The two font files it needs are committed as OFL `.ttf` subsets in `src/assets/fonts/` together with their `OFL.txt` licence (no new dependency). This replaces the `/api/og` route (ADR-028; `ARCHITECTURE.md` updated in this spec's PR): no route takes free-text query parameters to draw images.
12. **Stale data and errors**:
    - Cached reads that fail are cached briefly (`cacheLife({ stale: 30, revalidate: 30, expire: 300 })`, the settings pattern) and the page renders what it has: a homepage section with no data is left out, the footer keeps working.
    - A detail page whose read fails (an error, not a missing row) throws to the route's `error.tsx` (friendly message, "Thử lại" with `reset()`, hotline and Zalo from settings, reported to Sentry). It never answers 404 on an error, which would be cached and could drop the page from search.
    - The live departures section has its own error boundary: "Chưa tải được lịch khởi hành" with a retry button and the hotline, while the rest of the page stays.
    - Nothing shows a "last updated" time; listing prices are labelled "Từ" (indicative, `tour-listing.md` §1.3).
13. **CSP per page type** (`src/lib/csp.ts`, unit-tested; ADR-027):
    - Cached public pages: a nonce-free policy set as a header in `next.config.ts` for public paths: `default-src 'self'; script-src 'self' 'unsafe-inline'` (Next.js inline bootstrap scripts cannot carry a nonce on cached pages), `style-src 'self' 'unsafe-inline'`, `img-src 'self' data: blob: <supabase host>`, `font-src 'self'`, `connect-src 'self' <supabase host> <sentry ingest host>`, `frame-src 'none'`, `object-src 'none'`, `base-uri 'self'`, `form-action 'self'`, `frame-ancestors 'none'`, and `upgrade-insecure-requests` only when the Supabase URL is `https:` (a local `http://127.0.0.1` Supabase would otherwise be rewritten to https and fail). GA4/GTM hosts are added with consent mode in Phase 6.
    - Admin, account and checkout: **option 2 of ADR-027, chosen after the PR H spike**: the root layout of these routes exports `instant = false` and awaits `connection()` before rendering markup, so nothing is prerendered; the proxy generates a nonce per request and sends `script-src 'self' 'nonce-…' 'strict-dynamic'`, which Next.js applies to every script. Hash-based CSP with `experimental.sri` was ruled out (inline bootstrap and streamed scripts cannot be hashed; 7–17 violations per page in the spike). Account and checkout sit under the shared `[locale]` root layout today, so Phases 4–5 give them their own root layout (a route group with a separate root, like admin) or run a new spike.
    - `/auth/*` (the starter staff sign-in until Phase 5): the public nonce-free policy.
    - PR M confirms option 2 on the Turbopack build in CI (it cannot run locally).
    - Admin adds the Supabase Storage host to `connect-src` for signed uploads in every option.
    - Hosts come from validated env (`NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SENTRY_DSN`), never hard-coded. E2E fails on any `securitypolicyviolation` event, whichever option ships.
14. **Redirects**: the proxy looks up the request path in Upstash Redis for public `GET`/`HEAD` requests before locale routing and answers with the stored status when found. The format is Stream A's (Phase 2 PR #17): a hash `redirects` whose field is the source path and whose value is `{"to": "/target", "status": 301}`, read with `HGET redirects <path>`; a missing field means no redirect. Values read from Redis are untrusted: `to` must pass the same site-path rules as the admin (`isSitePath` in `src/modules/content/redirects.schemas.ts`), is never percent-decoded, and only status 301 or 302 is honoured; anything else is ignored and logged. It uses a 50 ms timeout and fails open; a 60-second in-memory cache per instance holds hits and also misses, so a redirect added in the admin can take up to a minute to apply on an instance that recently saw that path. Without `UPSTASH_REDIS_REST_URL`/`_TOKEN` it is a no-op (logged once). `hits` counting stays out (P1).
15. **Policy and fixed pages**: `pages.key` `about` and `faq` render at their fixed routes (`/ve-chung-toi`, `/cau-hoi-thuong-gap`); `terms`, `privacy`, `cancellation` and `payment` render at `/chinh-sach/[slug]` with their translation slugs. A cached `getPolicyLinks(locale)` (tag `pages`) gives the footer and the cookie banner the real paths; a policy without a published translation is left out of the footer, and the cookie banner's privacy link falls back to the contact page until the privacy page is published (the Phase 6 checklist requires all four policies in both languages).
16. **Initial JS budget** (150 KB gzip on public pages; ≈ 179 KB measured in Phase 1):
    - the desktop navigation is a disclosure without Radix (a button and a panel of links), so the header adds almost no JavaScript (PR I; this replaces loading the panel on first hover);
    - no next-intl client provider, tailwind-merge or `next/image` client code on public pages (ADR-029); measured in PR I: home 179 → 146.6 KB, tour page 194.3 → 148.8 KB (local webpack build);
    - the floating contact button's client code loads after idle;
    - gallery lightbox and mobile filter sheet load on first open; FAQ uses native `<details>` (no JS);
    - CI measures the gzip size of the JavaScript loaded by `/` and one tour detail page from the production build (`scripts/check-js-budget.mjs`): a warning from PR H, a failure from PR M.
17. **Draft preview and day images** (moved from Phase 2 PR D): `/admin/tours/[id]/preview?locale=vi|en` renders the public tour components for staff with the session client (drafts visible through staff RLS), uncached, `noindex`, behind `requirePermission("tours.read")`. Itinerary days may show one image from `media_ids`; PR H adds a MediaPicker per day in the tour editor's itinerary cards and extends the media delete usage check to itinerary `media_ids` (the Tiptap image scan stays with PR F).
18. **Hero search and travel styles**: the hero form submits `GET /tours?dest=<key>&month=<yyyy-mm>&style=<key>`. `style` is a new listing filter (`tour-listing.md` §1.4 had it out of scope): multi-select on travel style keys, matching tours linked to any of them, with its own filter group. The homepage hero image is an optional `homepage.hero.media_id` in the `homepage` setting (shape agreed with Stream A for PR G's settings editor); without one the hero is the navy band.
19. **Trust bar and testimonials** use only real data: the licence number and legal name from `settings.company`, contact hours from `settings.contact`, fixed copy for payment methods; an item whose data is missing is left out. Testimonials are approved, featured reviews; without any the section is left out. No invented statistics.
20. **Departure notes** are public: `departures.note` is readable by anon through the existing policy, so the public table shows it (for example "Mùa hoa anh đào"). **Dependency**: Stream A adds a "shown to customers" hint to the note field of the departure editor before PR H merges (the coordinator has asked for it). Internal remarks go in internal notes (Phase 4).
21. **Reviews on the tour page**: `ReviewSummary` shows the tour's approved reviews (`reviews.status = 'approved'`, `tour_id` = the tour; explicit columns, never `booking_id`), newest first, up to three, with the count and the average rating; verified reviews carry a "verified" label. Hidden when the tour has none. Cached with the `reviews` tag. `AggregateRating` in JSON-LD waits for P1 (verified reviews only).
